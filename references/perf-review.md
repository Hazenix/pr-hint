# 性能机会的源码检查

目标是找到小范围、行为可保持、能解释工程收益的优化 PR。先确认入口和调用链，再判断哪些工作可以省掉。下面的模式用于引导检查，候选须有当前源码证据和现实触发条件。

## 从调用入口发现成本

在本轮范围内优先看消息发送、工具调用、帧或视图构建、定时任务、列表加载和数据库查询。记录哪些操作会重复触发，以及成本受活跃对象数量、历史长度、schema 数量或数据行数中的哪些因素影响。沿调用链检查已有缓存、过滤、索引和批处理。

| 模式 | 源码检查方向 | 必须确认的行为边界 |
|---|---|---|
| 重复编译 | 每次工具调用重新编译同一个 schema 的 validator、解析器或模板 | 编译选项、schema 身份与可变性、校验错误和并发状态 |
| 重复解析 | 同一 JSON 文本、配置或序列化对象在循环、帧和请求中反复解析 | 缓存键覆盖全部输入，修改后的值及时生效，返回对象共享是否造成污染 |
| 读取范围过大 | 构建当前画面或状态时拉取全部历史，再过滤出活跃项 | 活跃项定义、顺序、删除、恢复和历史回退是否一致 |
| 无效遍历与查询 | 每次发送都扫描所有任务线程，再逐个检查是否有待答问题；循环中的 N+1 查询 | 提前筛选依据是否最新，批量读取是否保留一致性和必要副作用 |
| 周期扫描 | 定时轮询、救援任务或文档扫描总是扫全表，固定条件只命中少量行 | 实际 SQL、既有索引、数据库版本、参数及部分索引谓词匹配 |
| 重复派生和分配 | 每次事件或渲染重复排序、聚合、构建相同大对象或复制集合 | 输入变化、失效条件、执行频率和分配量是否足以产生实际收益 |

按实际架构选用相关模式，在账本注明已查路径和不适用原因。用户指定的范围内继续检查其他合理模式。

## 候选成立需要的证据

每个 perf 候选都要说明以下内容。

1. 谁在什么操作下触发，实际调用哪些函数或 SQL，下游如何使用结果。
2. 现在具体多做了什么，重复次数、扫描量、查询数或分配量如何随调用频率和数据规模增长。说明现实中可出现的输入规模及依据。
3. 最小改动如何消除这部分工作，以及为什么结果、顺序、错误、状态更新和副作用仍然正确。
4. 至少一项能支持成本判断的证据，例如真实调用链上的操作计数、查询计划、profile、基准，或由源码明确推导的重复次数与复杂度。只有看到 `JSON.parse`、循环或缺少显式缓存时，继续追踪触发和成本后再决定。

源码已证明每次请求重复编译 K 次、读取 N 条历史而只消费 A 条活跃记录，或扫描与历史长度线性增长时，可以形成候选。报告写明已证实的处理量变化和待测的耗时收益。缺少现实触发条件、规模依据或行为等价证据时，列为待验证。

## 针对优化方式核对风险

- 缓存需说明键、生命周期、失效、容量或释放方式，检查并发、可变对象、错误缓存和跨用户数据隔离。按 schema 缓存时核对 schema 是否稳定以及编译配置是否相同。
- 提前过滤、批量读取和只取活跃记录，需保留可见顺序、事务一致性、删除或恢复语义及原循环承担的副作用。使用缓存状态做过滤时，确认更新时机。
- 数据库索引需对照迁移和现有索引，使用代表性数据检查 `EXPLAIN` 或对应数据库的查询计划，考虑选择性、排序、写入成本和迁移方式。未运行查询计划时写明预期及验证缺口。

## 验证与交付

优先复用现有测试、基准和项目运行环境，调研阶段可在仓库外运行临时脚本或只读查询，遵守任务的源码修改边界。

- 对同一输入检查优化前后输出、顺序、错误和副作用，包含空输入、更新和删除、重复调用及与候选相关的并发情形。
- 能运行时记录基准提交、环境、数据规模、执行次数，以及优化前后耗时、内存、读取行数、查询数或编译次数中相关的指标。区分冷启动与重复调用，耗时比较重复采样。
- 尚未实现优化时，明确区分当前基线、理论工作量变化和未来验收方案。缺少环境时保留有证据的候选并注明未测项。
- 根据实际负载和节省的工作判断优先级。简历价值写清独立交付边界及可验证收益，百分比使用实测结果。

候选成立后按主流程定向检查相关 Issue、全状态 PR 和提交历史，搜索行为及文件路径，覆盖没有 `perf` 标签或对应 Issue 的实现。截图或历史已合并 PR 可帮助理解优化类型，推荐仍以当前未解决的成本为依据。
